# Experiment methodology

This document is the technical source of truth for how the Azure AI Search
`semantic_query` comparison was generated, indexed, searched, evaluated, and
reported. It is intentionally more detailed than the README and whitepaper so a
reviewer can trace the result back to inputs, code paths, parameters, and
artifacts.

## 1. Research question and decision rule

The experiment isolates one question:

> If L1 retrieval uses one query string and L2 semantic ranking receives a
> separate `semanticQuery` string, does ranking quality improve?

The primary predefined contrast is:

| Arm | Retrieval query | Semantic ranking query |
| --- | --- | --- |
| `hybrid_semantic_query_control` | `query.search_text` | `query.search_text` |
| `hybrid_semantic_query_deterministic` | `query.search_text` | `query.semantic_intent` |

The primary metric is **NDCG@10**. The predefined decision rule in
[`docs/preregistration.md`](preregistration.md) required the deterministic arm to
beat the identical-control arm by at least `+0.02` mean paired NDCG@10 and for
the paired bootstrap 95% confidence interval to be entirely above zero.

The final run did not meet that rule. The observed primary delta was `-0.0237`
with a paired bootstrap 95% CI of `[-0.0340, -0.0133]`, recorded in
[`reports/final/statistical-summary.json`](../reports/final/statistical-summary.json).
The Wilcoxon signed-rank secondary view is also recorded there: normal
approximation with continuity correction, zero deltas excluded, `z = -3.0048`,
two-sided `p = 0.0027`.

## 4. Data generation

### 4.1 Generator code path

Data generation is implemented in:

```text
src/semantic_query_experiment/data_generation/generator.py
```

The CLI entry point is:

```text
src/semantic_query_experiment/commands/generate_data.py
```

The full generation command used:

```powershell
uv run semqry-generate-data --chunk-count 10000 --seed 20260507
```

The generator rounds the requested chunk count up to whole three-document cases:

```text
case_count = (requested_chunk_count + 2) // 3
```

For `10000`, this produced:

| Artifact | Count |
| --- | ---: |
| source facts | 3334 |
| corpus chunks | 10002 |
| query specs | 3334 |
| relevance labels | 10002 |
| hard-negative chunks | 6668 |

### 4.2 Domain schema

Each case is built from deterministic combinations of:

| Dimension | Values |
| --- | --- |
| Products | `Asterol API`, `Vascorin XR`, `Neuroquel Sterile`, `Immunavax Fill`, `Cardioban Granulate` |
| Sites | `Dublin`, `Raleigh`, `Singapore`, `Uppsala`, `Toronto` |
| Document types | `deviation_investigation`, `capa_plan`, `batch_record`, `quality_audit`, `change_control`, `stability_trend`, `validation_summary`, `data_integrity_memo`, `sop` |
| Issue families | bioburden, OOT assay drift, ALCOA+ attribution, CIP conductivity, environmental monitoring, hold-time breach, process validation risk, complaint trending |
| Identifiers | deterministic `DEV-*`, `BATCH-*`, `SOP-*`, and revision-style identifiers |

The source fact schema records the product, site, document type, primary and
secondary identifiers, jargon term, plain-language term, answer action,
effective date, and superseded identifier.

### 4.3 Three-document case design

Each generated case emits exactly three chunks:

| Chunk | Relevance label | Purpose |
| --- | ---: | --- |
| Gold chunk | `3` | Contains the asserted answer-bearing fact and expected answer span. |
| Sibling hard negative | `2` | Same product/site/topic/jargon but different batch/root cause; useful context but not the answer. |
| Lexical hard negative | `1` | Shares identifiers and keywords but is an explicitly rejected draft. |

The generator does not emit explicit `0` labels for every other corpus document.
During evaluation, any returned document absent from a query's label map is
treated as relevance `0`.

The lexical hard negative is intentionally graded `1`, not `0`, even though it
is not the answer. It is topically useful context because it shares identifiers,
issue wording, and corrective-action language, but it should not satisfy the
question because the draft is explicitly rejected. This choice means
`Recall@50`, which treats any label greater than zero as relevant, measures
recovery of gold, sibling context, and lexical-trap context rather than gold-only
answer recovery.

### 4.5 `search_text` and `semantic_intent`

Every query stores two strings:

| Field | Meaning |
| --- | --- |
| `search_text` | L1 retrieval string used for BM25, hybrid keyword text, and query embeddings. |
| `semantic_intent` | Rule-based plain-language intent used only by the deterministic `semantic_query` arm. |

Examples from the generated query suite:

| Category | `search_text` | `semantic_intent` |
| --- | --- | --- |
| `id_lookup` | `DEV-10000 CAPA "bioburden excursion" Asterol API` | `Which action resolved the microbial contamination event for Asterol API at Dublin?` |
| `fielded_filter` | `doc_type:capa_plan product:"Vascorin XR" site:"Dublin" CAPA outcome` | `Which action resolved the unexpected potency trend for Vascorin XR at Dublin?` |
| `acronym_expansion` | `ALCOA trend required protocol amendment Neuroquel Sterile` | `Which action resolved the data integrity authorship issue for Neuroquel Sterile at Dublin?` |
| `synonym_swap` | `rinse verification failure remediation quality unit disposition` | `Which action resolved the rinse verification failure for Immunavax Fill at Dublin?` |
| `lexical_trap` | `DEV-10004 approved final corrective action environmental monitoring alert` | `Which action resolved the cleanroom microbial alert for Cardioban Granulate at Dublin?` |
| `long_compliance` | `Under GxP expectations, identify the final effectiveness action that closed the investigation for material storage time excursion at Raleigh.` | `Which action resolved the material storage time excursion for Asterol API at Raleigh?` |
| `short_operational` | `Vascorin XR process validation residual risk fix` | `Which action resolved the continued process verification concern for Vascorin XR at Raleigh?` |
| `caption_answer` | `answer passage for DEV-10007 effectiveness check` | `Which action resolved the market feedback quality signal for Neuroquel Sterile at Raleigh?` |
| `temporal_supersession` | `BIO-REV-01 superseded effective 2025-09-09` | `What currently effective action replaced BIO-REV-01?` |

Only `fielded_filter` also emits structured Azure Search filters in the query
spec. The runner translates `product`, `site`, and `doc_type` filter values into
OData `eq` clauses when present.

### 4.6 Corpus manifest and hash checks

The manifest at `reports/data-generation/corpus-manifest.json` records:

- seed
- requested and actual chunk count
- source fact count
- query count
- hard-negative count
- category counts
- local BM25 corpus-difficulty NDCG@10
- SHA-256 hashes for source facts, chunks, queries, and labels

The current CLIs record these hashes but do not automatically fail a later step
if a hash differs. Reproducers should compare the manifest hashes to regenerated
artifacts when auditing exact identity.

The local BM25 difficulty check is implemented in
`src/semantic_query_experiment/data_generation/bm25.py`. It tokenizes lowercase
alphanumeric, hyphen, and underscore terms with:

```text
[a-z0-9]+(?:[-_][a-z0-9]+)*
```

It then ranks chunks with a deterministic BM25 implementation over chunk text
plus keywords. This check is a corpus-quality gate and not the Azure AI Search
BM25 result-bearing arm.

### 5.3 Real embedding path

The full run used Azure OpenAI embeddings:

| Setting | Value |
| --- | --- |
| Endpoint | `https://semqry-ai-556dc8sc.cognitiveservices.azure.com` |
| Deployment | `text-embedding-3-large` |
| API version | `2024-10-21` |
| Dimensions | `3072` |
| Provider sentinel | `azure-openai:text-embedding-3-large:text-embedding-3-large:2024-10-21` |

The embedding client validates:

- response model equals `text-embedding-3-large`
- one embedding is returned for each input
- vector length equals 3072
- embeddings are cached by SHA-256 content hash
- cached records include model, deployment, API version, dimensions, vector hash,
  vector, and prompt token count where returned

Embedding requests retry HTTP `404`, `429`, `500`, `502`, `503`, and `504` up to
five attempts with exponential backoff or `Retry-After` when present. The `404`
retry was added because Azure returned transient `DeploymentNotFound` responses
during the long embedding job even after the deployment was healthy.


```powershell

  --embedding-mode azure-openai `
```

Before upload, the CLI:

1. Reads `data/generated/corpus-chunks.jsonl`.
2. Builds or loads embeddings.
3. Converts chunks to Azure Search documents.
4. Validates vector dimensions and embedding provider.
5. Writes a local document preview.
6. Validates the live index has the expected vector dimensions.
7. Uploads with `mergeOrUpload`.
8. Writes a resumable checkpoint of succeeded document IDs.

The full run uploaded 10,002 documents to the real embedding index.



Query vectors are embedded from `query.search_text` for every query. The same

### 6.2 Executed arms

The full run executed these six arms:

| Arm | Azure Search request shape |
| --- | --- |

## 7. Evaluation

Evaluation is implemented in:

```text
src/semantic_query_experiment/evaluation.py
src/semantic_query_experiment/commands/render_report.py
```

The report command used:

```powershell
uv run semqry-report `
  --results reports\runs\full-suite\results.jsonl `
  --output-dir reports\final
```

The evaluator joins:

| Input | Purpose |
| --- | --- |
| `data/queries/query-suite.jsonl` | Query categories and query IDs. |
| `data/labels/relevance-labels.jsonl` | Graded relevance by query/document. |
| `reports/runs/full-suite/results.jsonl` | Ranked results by arm/query/rank. |

Unlabeled returned documents are treated as relevance `0`.

### 7.1 Metrics

For each arm/query pair, the evaluator computes:

| Metric | Definition |
| --- | --- |
| `ndcg_at_3` | NDCG using top 3 results and graded relevance. |
| `ndcg_at_10` | NDCG using top 10 results and graded relevance. |
| `mrr_at_10` | Reciprocal rank of the first exact answer-bearing document (`relevance == 3`) in top 10. |
| `recall_at_50` | Fraction of all labeled relevant documents (`relevance > 0`) found in top 50. |
| `hit_at_1` | Whether any exact answer-bearing document appears in top 1. |
| `hit_at_3` | Whether any exact answer-bearing document appears in top 3. |
| `hit_at_5` | Whether any exact answer-bearing document appears in top 5. |
| `hit_at_10` | Whether any exact answer-bearing document appears in top 10. |
| `latency_ms` | Elapsed milliseconds measured for the query-arm Search request. |

NDCG uses the standard graded gain:

```text
gain = 2^relevance - 1
discount = log2(rank + 1)
NDCG@k = DCG@k / ideal_DCG@k
```

Aggregate metrics are arithmetic means over query-level metrics. Category
metrics are arithmetic means grouped by `arm` and `category`.

### 7.2 Primary delta and bootstrap

`metrics.json` records the paired primary delta:

```text
hybrid_semantic_query_deterministic.ndcg_at_10
- hybrid_semantic_query_control.ndcg_at_10
```

for every query present in both arms.

`statistical-summary.json` adds a paired nonparametric bootstrap:

| Setting | Value |
| --- | --- |
| Bootstrap unit | query-level NDCG@10 delta |
| Seed | `20260507` |
| Iterations | 5000 |
| Confidence level | 95% |
| Observed mean delta | `-0.023695073784271565` |
| CI lower | `-0.034022133359294084` |
| CI upper | `-0.013258986156984318` |
| Decision result | `not_supported` |

Category-level deltas in `statistical-summary.json` are exploratory point
estimates. They are not multiple-comparison corrected and should not be read as
formal per-category significance claims.

## 8. Final result summary

Aggregate metrics from the full run:

| Arm | NDCG@10 | NDCG@3 | MRR@10 | Recall@50 | Hit@1 | Hit@5 | Hit@10 | Mean latency ms |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `hybrid_semantic` | 0.3698 | 0.3397 | 0.3822 | 0.4505 | 0.3503 | 0.4169 | 0.4931 | 582.8 |
| `hybrid_semantic_query_control` | 0.3698 | 0.3397 | 0.3822 | 0.4505 | 0.3503 | 0.4169 | 0.4931 | 582.6 |
| `hybrid_semantic_query_deterministic` | 0.3461 | 0.2802 | 0.3383 | 0.4505 | 0.2564 | 0.4472 | 0.5504 | 582.9 |
| `bm25` | 0.2823 | 0.2585 | 0.2196 | 0.4384 | 0.0612 | 0.3809 | 0.4223 | 244.3 |
| `hybrid` | 0.1657 | 0.1229 | 0.1764 | 0.4505 | 0.1419 | 0.1998 | 0.3221 | 549.1 |
| `vector` | 0.0495 | 0.0279 | 0.0461 | 0.1529 | 0.0198 | 0.0762 | 0.1314 | 321.0 |

The most important interpretation details:

1. The primary predefined hypothesis was not supported.
2. Conventional hybrid semantic ranking was the strongest aggregate arm.
3. `hybrid_semantic` and `hybrid_semantic_query_control` had identical quality
   metrics, which validates the control: setting `semanticQuery` equal to the
   normal search text behaved like omitting a separate semantic query.
4. The separate rule-based `semantic_query` arm improved deeper Hit@5 and Hit@10
   but reduced Hit@1 and aggregate NDCG@10.
5. Exploratory category analysis suggests separate semantic intent helped
   fielded/filter, long compliance, short operational, synonym, and acronym
   categories.
6. The same exploratory analysis shows large losses for identifier lookup and
   temporal supersession.
7. Hybrid Recall@50 was only about `0.4505` across semantic arms. This is low for
   a three-label-per-query setup and likely reflects the deliberately dense
   hard-negative corpus, where thousands of other query cases share product,
   site, jargon, and corrective-action language. It should be treated as a
   limitation and investigated before production generalization.
8. The vector-only and non-semantic hybrid baselines were weak; future work
   should treat vector query construction and fusion weighting as open tuning
   questions, not as optimized production baselines.

## 10. Limitations

This experiment is reproducible and transparent, but it is still synthetic.
Important limitations:

- Corpus content, labels, queries, and hard negatives are generated from the
  same structured source facts.
- Labels are generator-asserted, not human-adjudicated.
- Category-level results are exploratory and not multiple-comparison corrected.
- The LLM rewrite arm was not run.
- The vector-only and non-semantic hybrid baselines were not tuned as production
  baselines.
- The preregistered latency warmup and percentile protocol was not followed in
  this run. Reported latency is the uncalibrated single-shot mean per arm from
  the measured Search requests; p50/p95/p99 latency reporting is not yet
  included in the final artifact.
- The raw record-level results are not in git because of file size; publish them
  separately if an audit requires every returned rank.

The recommended production next step is to repeat the same primary contrast on
representative real content, with human-reviewed labels and category-aware
semantic query rules that preserve identifiers and temporal constraints.
